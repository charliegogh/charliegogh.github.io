# 性能优化和错误收集上报

最近迁移静态资源到CDN后，我们频繁收到页面崩溃的反馈，经过排查发现服务器返回给前端的资源在传输过程中被截断，直接导致了程序的崩溃。碍于桌面端控制台访问的限制，初期我们无法及时捕获这些错误。为此，我们采取了错误收集的措施，并协调实施资源在传输过程中的并行压缩（gzip），效果十分显著，这项改进不仅显著提升了系统性能，还在错误收集方面展现出了明显的实际效果。

当谈到前端领域时，性能始终是一个至关重要的议题，因为它直接决定了产品体验的优劣。尽管我们无法保证程序永远不会出现问题，但监控性能数据、收集错误信息并将其上报到线上真实环境是至关重要的。这一系列操作可以让我们随时掌握线上产品的状态，从而优化应用程序的体验，这对于确保用户满意度和产品稳定性至关重要。

## gzip 常见的性能优化配置

gzip压缩在性能优化中是一项重要的策略，结合前端预压缩和服务端在线压缩可以充分发挥优势。配置nginx时，可以考虑以下方案：

1. 前端预压缩：使用构建工具（如Webpack、Gulp等）在前端生成.gz文件。
    - 优点：
        - 前期耗时，但减少了服务器压力。
        - 加载时不需要服务器实时压缩，提高了前端资源加载速度。
    - 缺点：
        - 打包后体积变大，占用更多存储空间。
        - 前期构建时间会增加。

2. 服务端在线压缩（nginx配置）：在nginx配置中启用gzip模块进行在线压缩。
    - 优点：
        - 不需要预先生成.gz文件，即时压缩，无需占用额外存储空间。
    - 缺点：
        - 实时压缩会消耗服务器性能。
        - 压缩过程可能导致轻微延迟，影响部分性能。

### 结合配置建议：

- 配置nginx：在nginx上进行配置，结合两种方式的优势。
- 条件判断：使用nginx配置判断请求是否存在对应的.gz文件，如果存在，直接返回该静态资源；如果不存在，才进行在线压缩。
- 动静分离：将动态资源和静态资源分开，对于静态资源，尽量利用已经预先压缩好的.gz文件；对于动态资源，根据需要实时压缩。

示例nginx配置：

```nginx
http {
    gzip on;
    gzip_comp_level 5;
    gzip_types text/plain text/css application/json application/javascript text/xml application/xml application/xml+rss text/javascript;

    server {
        listen       80;
        server_name  example.com;

        location / {
            root   /var/www/html;
            index  index.html index.htm;
            
            # 检查是否存在对应.gz文件，如果存在直接返回
            if (-f $request_filename.gz) {
                add_header Content-Encoding gzip;
                rewrite (.*) $1.gz break;
            }

            # 不存在.gz文件，进行在线压缩
            try_files $uri @missing;
        }

        location @missing {
            gzip_static off;
            gzip on;
            ...
            # 其他压缩相关配置
            ...
        }
    }
}
```

这种结合方式可以充分利用已有的.gz文件，同时对于不存在预压缩文件的请求，实时进行在线压缩，达到压缩资源和减少服务器压力的双重优势。


## 错误信息收集

### window.onerror 错误收集

window.onerror 是一个全局的事件处理函数，用于捕获未被捕获的 JavaScript 错误。当 JavaScript 运行时发生未捕获的异常时，事件处理函数会被调用，允许开发者在发生错误时执行自定义的操作，比如记录错误信息或通知用户。

这个事件处理函数能捕获到以下类型的错误：

- 语法错误（Syntax Errors）： 如代码书写错误、拼写错误等导致的错误。
- 运行时错误（Runtime Errors）：在代码执行过程中发生的错误，比如变量未定义、类型错误等。
- 资源加载错误（Resource Errors）： 比如 script 或 img 加载失败。

```
window.onerror = function(message, source, lineno, colno, error) {
  // message: 错误信息
  // source: 出错的文件 URL
  // lineno: 出错代码所在的行号
  // colno: 出错代码所在的列号
  // error: 错误对象

  // 执行自定义的错误处理逻辑，比如记录错误日志或发送错误信息到后台
  console.error('发生错误:', message, '在', source, '的第', lineno, '行，第', colno, '列');
};
```

但是它有一些局限性：

1. 跨域问题：它无法捕获跨域脚本的错误。
2. 并不是所有的错误都能被捕获： 比如浏览器崩溃或内存溢出等一些严重的错误可能无法被捕获。
3. 错误信息有限： 对于一些错误，它提供的信息可能不够详细，无法提供足够的上下文来排查问题。

### 跨域脚本错误收集

当你需要统一脚本错误时，使用 crossorigin="anonymous" 是一种处理跨域脚本加载错误的方法。这个属性告诉浏览器去加载资源的时候不要带上用户的凭据（比如 cookie 或 HTTP 认证信息），这有助于防止跨域请求中的错误导致凭据泄露问题。

设置 crossorigin="anonymous" 可以避免这种情况，因为它告诉浏览器不要发送凭据，这样跨域资源加载时产生的错误就能更容易地被捕获和处理。

### 针对Promise的错误收集处理

当处理 JavaScript 中的 Promise 错误时，养成在每个语句之后添加 catch 函数的习惯是一个很好的实践。这样可以更好地捕获和处理可能发生的异常，保证代码的健壮性和可靠性。

使用 ESLint 可以帮助规范代码风格，确保这种习惯得到贯彻执行。可以配置 ESLint 来强制执行在每个 Promise 链式调用中都包含 catch 函数，以确保错误不被忽视。

### 处理网络加载错误

当使用 \<script> 或 \<link> 标签加载脚本或其他资源时，处理网络加载错误可以通过 window.addEventListener('error') 方法来实现。网络加载错误是指由于服务器问题、网络不稳定或资源不存在等原因导致请求失败的情况。

你可以针对元素添加 error 事件监听器来捕获加载异常，然后进行相应的处理。例如：

```javascript
window.addEventListener('error', function (event) {
  const target = event.target;
  if (target.tagName === 'SCRIPT' || target.tagName === 'LINK') {
    console.error('资源加载失败:', target.src || target.href);
    // 进行错误处理或其他操作
  }
});
```
这段代码会监听全局的 error 事件，当资源加载失败时，会触发该事件，其中 event.target 可以获取触发错误的元素，通过检查标签名和对应的资源地址，可以识别加载失败的资源，并进行相应的错误处理或记录。

### 页面崩溃错误收集

当构建一个成熟的系统时，除了处理 JavaScript 错误外，还需要收集页面崩溃和卡顿等信息，以便更全面地监控和改善用户体验。对于页面崩溃和卡顿信息的收集，可以结合监听 window 对象的 load 和 beforeunload 事件，并利用本地存储来实施监控。

通过监听 load 和 beforeunload 事件，并结合本地存储，可以收集页面崩溃和卡顿等信息，为系统的稳定性和用户体验提供更全面的监控和改进。

## 性能数据和错误信息上报

1. 单域名上报
    - 使用单域名，可以防止对主业务服务器造成压力，能够避免日志相关处理逻辑和数据在主业务服务器上的堆积。
2. 上报时机
   页面加载性能数据可以在页面稳定后进行上报，一般有如下 4 种常见。
    - 页面加载和重新刷新
    - 页面路由切换
    - 页面所在的 tab 标签重新变的可见
    - 页面关闭

- 针对单应用上报，只需监听hashchange事件监听路由变化进行适时上报；而如果是通过history API 改变URL实现，需要使用 pushState 和 replaceState 事件进行适时上报。

- 针对离开页面数据收集页面跳转不流程问题

推荐 sendBeacon 方法，navigator.sendBeacon 行为是异步的，在没有极端数据量和队列综述的限制下，会优先返回 true 以保证请求成功发送。
